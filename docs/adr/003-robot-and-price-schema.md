# ADR-003: схема robot и price

- Статус: предложено (нужно подтверждение владельца по трём вопросам ниже)
- Дата: 2026-08-26
- Linear: KIBER-42 / KP-060, вход для KIBER-44 / KP-061
- Схемы: `data/models/schema/robot-price.schema.json`, `data/models/schema/robot-pricing.schema.json`
- Проверка: `python3 scripts/validate_price_schema.py`
- Смежное решение: `docs/DECISIONS/003-controlled-rebuild-and-source-hierarchy.md` (два регистра решений стоит свести в один — KIBER-14)

## Контекст

Цена — единственные данные на сайте, ошибка в которых стоит денег напрямую. Аудит 24 роботов
(`docs/robot-price-audit.md`, KIBER-44) сравнил три независимых источника — текст живой
production-страницы, карточку каталога и внутренний источник истины — и показал:

- **21 из 24** роботов имеют расхождение между источниками;
- **15 из 24** часовых ставок в источнике истины равны дневной цене, делённой на 8 (Unitree G1:
  100 000 ₽ / день → 12 500 ₽ / час), и **ни разу** не встречаются на сайте. Это вычисленная
  ставка, а не тариф, подтверждённый бизнесом;
- сайт при этом публикует свою часовую ставку, равную примерно дневной цене ÷ 4 — то есть в ходу
  две разные синтетические ставки;
- у 2 роботов (`arenda-robota-sofiya`, `arenda-unitree-h2`) цены нет нигде, но структура данных
  всё равно ожидает сумму.

Схема контента новой сборки (`src/content/schemas.ts`, PR #8) описывает цену как `mode` плюс
свободную строку `display`. Такая модель не умеет отличить подтверждённую цену от вычисленной и не
хранит ни единицу, ни минимальный заказ, ни дату актуальности — то есть не закрывает критерий
KP-060 «сумма, единица, минимум, status, valid_from; unknown не угадывается».

## Решение

Каноническая ценовая запись описывается JSON Schema и содержит:

| Поле | Назначение |
|---|---|
| `status` | `approved` / `needs_review` / `unknown` — единственный признак, разрешающий публикацию |
| `amount` | сумма в целых рублях; обязательна при `approved`, запрещена при `unknown` |
| `currency` | всегда `RUB` |
| `unit` | `hour` / `day` / `shift` / `event` / `package` |
| `qualifier` | `from` или `exact` — «от суммы» перестаёт быть частью текста |
| `minimum` | минимальный заказ; `null` = минимума нет, а не «неизвестен» |
| `display` | текст для пользователя, выводимый из `amount`/`unit`/`qualifier` |
| `validFrom` / `validUntil` | срок действия цены |
| `source` | `live-site` / `tariff-table` / `manager` / `contract` / `derived` + ссылка и дата съёма |
| `owner`, `reviewedOn` | кто подтвердил сумму и когда |

Правила, которые схема принуждает соблюдать:

1. **Неизвестная цена остаётся неизвестной.** `status: unknown` требует `amount: null` и
   `display: «Цена по запросу»`. Подставлять сумму «по аналогии» нельзя.
2. **Вычисленная цена помечает себя вычисленной.** `source.type: derived` обязателен для любой
   пересчитанной суммы и требует `derivedFrom` — ссылки на подтверждённую шкалу, из которой сделан
   пересчёт. Часовая ставка «дневная ÷ 8» без такой шкалы схему не проходит.
3. **Публикуется только подтверждённое.** `publish: true` в блоке `robot-pricing` допустим лишь при
   `primary.status: approved`; при `approved` обязательна дата `reviewedOn`.
4. **У каждой цены есть источник и владелец.** Запись без `source.ref` и `owner` невалидна.

Робот в контенте остаётся идентифицируемым по `slug`, совпадающему с production-путём
(`arenda-unitree-g1`), — это зафиксировано реестром URL в KIBER-41 и не пересматривается здесь.

## Что это значит для новой сборки

Схему `src/content/schemas.ts` менять в рамках этой задачи не нужно — файл принадлежит PR #8.
Предлагаемая дельта для его владельца:

```diff
 pricing: z.object({
-  mode: z.enum(['calculated', 'from', 'fixed']),
+  status: z.enum(['approved', 'needs_review', 'unknown']),
+  amount: z.number().int().min(1000).nullable(),
+  unit: z.enum(['hour', 'day', 'shift', 'event', 'package']),
+  qualifier: z.enum(['from', 'exact']),
+  minimum: z.object({ value: z.number().positive(), unit: z.enum(['hour','day','shift','event']) }).nullable(),
+  validFrom: z.iso.date(),
+  source: z.object({ type: z.enum(['live-site','tariff-table','manager','contract','derived']), ref: z.string().min(1), capturedAt: z.iso.date(), derivedFrom: z.string().optional() }),
+  owner: z.string().min(1),
   currency: z.literal('RUB'),
   display: z.string().min(1),
-  factors: z.array(z.enum(['duration', 'program', 'logistics'])).min(1),
   public_offer: z.literal(false),
   disclaimer: z.literal('Не является публичной офертой'),
 })
```

Пилотная запись `src/content/robots/unitree-g1.yaml` сейчас содержит `display: от 150 000 ₽`, тогда
как сайт показывает `100 000 ₽ / день`, а карточка каталога — `от 50 000 ₽`. По этой схеме такая
запись обязана иметь `status: needs_review` и не публиковаться до решения владельца.

## Последствия

- 21 робот не может быть опубликован с ценой до разбора конфликтов (KIBER-44).
- Роботы без подтверждённой цены показывают «Цена по запросу» — это допустимое состояние, а не
  дыра в данных.
- Любая часовая ставка требует отдельного бизнес-решения: сейчас ни одна из двух используемых не
  подтверждена.

## Требуется решение владельца

1. Публикуем ли часовую ставку вообще — или на сайте остаются только дневные цены и пакеты?
2. Минимальный заказ: в тарифной таблице есть позиция «2 часа». Это минимум для публичной ставки?
3. Кто владелец цены (`owner`) по умолчанию и как часто перепроверяется `validFrom`?
