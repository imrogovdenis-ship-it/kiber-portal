Дата: 2026-08-25  
Статус: `consolidated_site_architecture_spec`  
Документ: единое ТЗ на создание сайта КИБЕР ПОРТАЛ «с нуля» как конечной системы, без поэтапного плана работ.

## 0. Назначение документа

Этот документ описывает не этапы разработки, а целевую архитектуру сайта КИБЕР ПОРТАЛ:

- бизнес-роль сайта;
- информационную архитектуру;
- типы страниц;
- компонентную систему;
- структуру данных;
- SEO-архитектуру;
- медиабиблиотеку;
- формы и лидогенерацию;
- чат-ботов и внутренних агентов;
- аналитику и события;
- интеграции;
- юридический слой;
- quality gates и production boundaries.

Цель документа — дать команде разработки, редакторам и AI-ассистентам единое представление о полном объёме сайта и его компонентов.

## 1. Назначение сайта

### 1.1. Главная бизнес-цель

Главная цель сайта — **получать заявки на аренду роботов**.

Сайт должен быть не просто каталогом и не просто блогом, а коммерческой системой, которая:

- объясняет, какие роботы доступны;
- помогает выбрать робота под событие;
- вызывает доверие;
- переводит посетителя в контакт с менеджером;
- поддерживает SEO-трафик по коммерческим и информационным запросам;
- создает удобную платформу для трафика из Яндекс.Директ;
- становится базой знаний для публичного чат-бота Кибер Гоши (маскот сайта и бренда) и внутреннего ИИ ассистента.

### 1.2. Дополнительные цели

Дополнительные цели сайта:

1. **SEO-трафик**  
   Привлекать коммерческий и информационный трафик по запросам аренды/проката роботов, конкретных моделей, сценариев мероприятий и новостей робототехники.

2. **Доверие и портфолио**  
   Показывать реальные роботы, фото, кейсы, юридические данные, понятный процесс аренды, ответы на вопросы и proof-контент.

3. **Каталог как витрина**  
   Давать быстрое представление о роботах, сценариях и возможностях, даже если итоговая цена и подбор уточняются менеджером.

4. **Редакторская и агентская управляемость**  
   Сайт должен быть удобен для обновления через GitHub и ассистента Гефеста после подтверждения изменений.

5. **Продажа товаров**  
   Сайт должен иметь удобны интернет магазином для продажи запчастей и аксессуаров для роботов.

### 1.3. Conversion actions

Главный conversion action:

```text
Написать нам в мессенджер
```

Дополнительные conversion actions:

- отправить форму заявки;
- позвонить;
- подобрать робота через чат-бота;
- скачать PDF-КП;
- перейти в карточку робота из каталога/подборки/статьи;
- задать вопрос по конкретной странице или роботу.

### 1.4. Основная аудитория

Основная аудитория:

- event-агентства;
- корпоративные клиенты.

Дополнительная аудитория:

- частные мероприятия;
- выставки и форумы;
- рестораны и HoReCa;
- школы и детские события;
- организаторы промо-акций;
- подрядчики и партнёры по мероприятиям.

### 3.2. Обязательный будущий тип страниц: Кейсы

Раздел **Кейсы** является обязательным будущим типом страниц.

Кейс — это страница реального мероприятия или проекта, где фиксируются:

- название события;
- дата/период, если можно публиковать;
- город/площадка, если можно публиковать;
- робот или несколько роботов;
- сценарий использования;
- фотографии/видео;
- результат;
- отзыв или цитата, если есть разрешение;
- ссылки на карточки роботов и релевантные подборки;
- CTA «Повторить похожий сценарий».

Кейсы нужны как proof layer для доверия, SEO и sales enablement.

## 4. SEO-архитектура

### 4.1. Роли разделов в SEO

| Тип страницы | SEO-роль | Search intent |
|---|---|---|
| Главная | ВЧ: аренда/прокат роботов | Commercial / transactional |
| Карточки роботов | НЧ модельные запросы | Transactional / model-specific |
| Подборки | СЧ группы и сценарии | Commercial investigation |
| Блог Кибер Гоши | НЧ сценарные и идейные запросы | Informational + assisted commercial |
| Новости | Инфотрафик и узнаваемость | Informational / freshness |
| Кейсы | Proof + сценарные запросы | Commercial proof / trust |
| Контакты | Брендовые и доверительные запросы | Navigational / trust |

### 4.2. Региональная SEO-структура

Базовые регионы:

- Москва;
- Россия.

Региональная структура не должна плодить пустые doorway-страницы. Страницы формата:

```text
/robot-na-vystavku-v-moskve
/arenda-robota-na-svadbu-v-moskve
```

создаются только если есть:

- подтверждённые реальные запросы пользователей;
- достаточный уникальный контент;
- релевантный робот/сценарий;
- полезная коммерческая ценность;
- отсутствие каннибализации с подборками/статьями.

Такие страницы могут существовать как статьи, подборки или отдельные landing pages — решение зависит от intent.

### 4.3. Schema.org

Обязательные schema types:

- `Organization`;
- `WebSite`;
- `Service` для карточек роботов/услуг;
- `FAQPage` для страниц с FAQ;
- `BreadcrumbList`;
- `CollectionPage` для подборок и индексов;
- `BlogPosting` для статей;
- `ContactPage`;
- `NewsArticle` или `BlogPosting` для новостей — в зависимости от формата;
- `Product` допустим для магазина товаров, но не должен подменять аренду услуг.

### 4.4. Alt и media SEO

Для всех meaningful images нужен truthful alt.

Правила:

- сначала описываем, что реально видно;
- коммерческие ключи добавляем только если они соответствуют изображению и странице;
- не превращаем alt в список ключей;
- не добавляем неподтверждённые города, бренды, площадки, людей, кейсы;
- не пишем цены в alt;
- для каждой страницы/контекста должна быть достаточная коммерческая SEO-alt coverage по meaningful images.

### 4.5. PDF-КП и SEO

Отдельный SEO-слой для PDF-КП не является обязательным.

PDF-КП — это sales/support инструмент, который формируется на основе карточки робота/услуги и может включать:

- название робота/услуги;
- сценарии применения;
- что входит в аренду;
- требования к площадке;
- фото;
- ориентировочную цену или `цена по запросу`;
- контакты;
- юридическую пометку, если цена не является офертой.

PDF может быть закрыт от индексации или генерироваться по запросу, чтобы не плодить дубли SEO-страниц.

## 5. Page types

### 5.1. Home page

Задача главной:

- быстро объяснить, что КИБЕР ПОРТАЛ сдаёт роботов в аренду для мероприятий;
- показать каталог;
- дать быстрый CTA в мессенджер;
- направить в подборки;
- показать Кибер Гошу как голос бренда;
- дать вход в статьи/новости;
- создать доверие.

Обязательные блоки:

1. Header.
2. Hero с ВЧ positioning.
3. Каталог аренды роботов.
4. Цитата Кибер Гоши.
5. Подборки.
6. Статьи/Блог Кибер Гоши.
7. CTA/lead-flow.
8. Footer.

### 5.2. Robot rental card

Карточка робота — главная коммерческая endpoint-страница под модельный НЧ запрос.

Обязательные блоки:

1. Hero.
2. Короткий вводный текст с самой важной информацией.
3. Факты.
4. Сценарии применения.
5. Галерея.
6. Видео, если есть.
7. Тарифы/цена.
8. FAQ.
9. Похожие роботы.
10. Статьи про робота.
11. PDF-КП.
12. CTA.
13. Требования к площадке.
14. Что входит в аренду.
15. Доставка/оператор.
16. Юридическая пометка рядом с ценами.

Цены:

- основной вариант — цены могут быть скрыты, сайт ведёт в заявку;
- если цена показывается, используется формат `от X ₽ / час`;
- пакеты 1/4/8 часов показываются при необходимости;
- если цена неизвестна или зависит от условий, блок цены заменяется на `цена по запросу`;

### 5.3. Shop product card

Отдельно от аренды должен быть предусмотрен будущий каталог-магазин:

- продажа роботов;
- запасные части;
- АКБ;
- аксессуары;
- расходники;
- другие товары.

Карточка товара магазина не должна смешиваться с карточкой аренды.

Обязательные поля товара:

- title;
- slug;
- category;
- brand/model;
- availability status;
- price или request price;
- images;
- specs;
- compatibility;
- warranty/terms;
- CTA: купить/запросить наличие/получить консультацию.

### 5.4. Collection / подборка

Подборки — landing pages под заявки, но обязательно SEO-оптимизированные.

Архитектура должна позволять создавать любые тематические подборки в любое время.

Стартовые подборки:

- роботы-гуманоиды;
- роботы-собаки;
- роботы для свадьбы;
- роботы для выставки;
- роботы для корпоратива;
- роботы для промо;
- роботы-официанты;
- роботы-художники;
- роботы для детей;
- роботы для welcome-зоны;
- интерактивные роботы;
- роботы для ресторанов/HoReCa.

Обязательные блоки подборки:

1. Hero.
2. Короткое объяснение сценария.
3. Список подходящих роботов.
4. Рекомендации выбора.
5. Сценарии применения.
6. FAQ для SEO.
7. Внутренние ссылки на карточки роботов.
8. Ссылки на статьи и кейсы.
9. CTA «Написать нам» / «Оставить заявку».

### 5.5. Blog article

Раздел называется **Блог Кибер Гоши**.

Статьи решают задачи:

- scenario long-tail SEO;
- объяснить выбор робота;
- снять возражения;
- поддержать перелинковку к роботам и подборкам;
- дать материал для RAG-бота.

Обязательные блоки статьи:

- article hero;
- дата/обновление, если применимо;
- content body;
- related robots;
- related collections;
- related articles;
- FAQ, если релевантно;
- CTA.

### 5.6. News page

Новости — это объединённый слой:

- новости робототехники;
- новости КИБЕР ПОРТАЛА;
- AI-generated news pipeline;
- SEO-инфотрафик;
- узнаваемость.

Новости не должны публиковаться полностью автоматически без проверки.

Обязательные свойства новости:

- title;
- summary;
- source links;
- source reliability status;
- publication status;
- human review status;
- related robots/collections;
- Kiber Gosha style status.

### 5.7. Case page

Кейсы — обязательный будущий тип страниц.

Обязательные блоки кейса:

- hero с фото/видео;
- событие/формат;
- робот(ы);
- задача клиента;
- что сделали;
- результат;
- галерея;
- отзыв/цитата, если можно;
- связанные роботы;
- похожие сценарии;
- CTA.

### 5.8. Contacts page

Задачи контактов:

- доверие;
- реквизиты;
- быстрый звонок;
- мессенджеры;
- форма заявки;
- юридический слой.

Контактные данные должны опираться на юридические документы сайта и подтверждённые бизнес-данные.

### 5.9. Legal pages

Обязательные юридические страницы:

- политика обработки персональных данных;
- согласие на обработку персональных данных;

## 7. Design system

### 7.1. Источник визуального направления

Визуальный слой должен быть разработан с нуля, но основываться на существующем опубликованном сайте.

Требования:

- не копировать blindly generated HTML/CSS;
- извлекать реальные визуальные паттерны из опубликованного сайта;
- строить собственную design system на токенах и компонентах;
- сохранить узнаваемость КИБЕР ПОРТАЛА;
- улучшить структурность, mobile и SEO.

### 7.2. Базовые визуальные принципы

Нужно сделать анализ уже существующего сайта, что бы сформировать базовые визуальные принципы.

### 7.3. Responsive

Сайт должен проектироваться desktop/mobile одновременно.

Для каждого компонента должны быть определены:

- desktop layout;
- tablet behavior;
- mobile stacking;
- media crop rules;
- CTA placement;
- modal behavior;
- accessibility behavior.

## 8. Роль Astro в проекте

Astro является техническим ядром frontend/SEO-архитектуры КИБЕР ПОРТАЛА. Он не является CRM, Telegram-ботом, аналитическим сервисом или production-инфраструктурой. Его роль — превратить структурированные данные, контент и компоненты в быстрый статический сайт с SEO-ready HTML.

Целевая схема:

```text
GitHub source-of-truth
  ├─ robots
  ├─ shop products
  ├─ collections
  ├─ articles
  ├─ news
  ├─ cases
  ├─ media library
  ├─ SEO fields
  └─ integration contracts
        ↓
Astro
  ├─ layouts
  ├─ components
  ├─ pages/routes
  ├─ content rendering
  ├─ SEO head
  ├─ JSON-LD schema
  ├─ forms UI
  ├─ CTA contracts
  └─ static build
        ↓
app/dist
  ├─ HTML
  ├─ CSS
  ├─ images/assets
  ├─ sitemap
  └─ 404
        ↓
QA validators
        ↓
Docker/Nginx/Coolify production
```

### 8.1. Astro как генератор статического сайта

Astro должен собирать сайт в статический HTML по умолчанию:

```text
structured data + content collections + Astro components
→ static HTML pages
→ SEO-ready website
```

Это важно, потому что сайт должен хорошо индексироваться, быстро открываться, сохранять текст в HTML без обязательного runtime JavaScript и поддерживать много SEO-страниц: карточки роботов, подборки, статьи, новости, кейсы и юридические страницы.

SSR допускается только для функций, которым действительно нужен runtime, например для будущего backend/API слоя формы, если он будет реализован внутри той же платформы. Базовая публичная часть сайта должна оставаться static-first.

### 8.2. Astro как слой между данными и страницами

Astro-компоненты не должны хранить бизнес-факты вручную. Бизнес-факты должны жить в source-of-truth данных.

Неправильно:

```text
RobotPage.astro вручную содержит цену Unitree G1, FAQ и связанные статьи.
```

Правильно:

```text
data/content/model содержит факты робота
→ loader/helper нормализует данные
→ RobotPage.astro отображает их
→ validators проверяют rendered output
```

Astro должен быть отображающим и маршрутизирующим слоем, а не местом ручного копирования цен, реквизитов, alt-текстов, FAQ, связей и SEO-полей.

### 8.3. Astro layouts

Базовые layout-компоненты:

| Component | Роль |
|---|---|
| `BaseLayout.astro` | общий HTML shell, подключение SEO, header, footer, modal slots |
| `SeoHead.astro` | title, description, canonical, robots, OG/Twitter, JSON-LD |
| `Header.astro` | логотип, навигация, телефон, CTA |
| `Footer.astro` | footer navigation, контакты, legal links, CTA |
| `ContactMessengerModal.astro` | попап мессенджеров и формы |
| `CookieBanner.astro` | будущий слой согласия для Яндекс.Метрики |

### 8.4. Astro route generation

Astro отвечает за генерацию публичных маршрутов.

Примеры маршрутов:

```text
/
/arenda-unitree-g1
/arenda-bellabot
/roboty-gumanoidy
/arenda-robotov-na-meropriyatie
/articles
/news
/contacts
/privacy-policy

/404.html
```

Для карточек роботов и динамических content routes должен использоваться `getStaticPaths()` или эквивалентная статическая генерация из данных.

Принцип:

```text
новый робот добавлен в source-of-truth
→ Astro сгенерировал страницу
→ QA проверил SEO, links, schema, CTA
```

### 8.5. Astro и SEO

Astro должен централизованно формировать page-level SEO:

- `<title>`;
- meta description;
- canonical;
- robots;
- Open Graph;
- Twitter metadata;
- JSON-LD;
- H1;
- breadcrumbs;
- internal links;
- CTA contracts.

Schema по типам страниц:

| Page type | Schema |
|---|---|
| Home | `Organization`, `WebSite` |
| Robot rental card | `Service`, `FAQPage`, `BreadcrumbList` |
| Collection | `CollectionPage`, `BreadcrumbList`, FAQ при наличии |
| Blog article | `BlogPosting`, `BreadcrumbList` |
| News | `NewsArticle` или `BlogPosting`, `BreadcrumbList` |
| Contacts | `ContactPage`, `Organization` |
| Legal | `WebPage` или базовый page schema при необходимости |

### 8.6. Astro и дизайн-система

Astro должен использовать собственную design system проекта:

```text
tokens.css
base.css
components.css
global.css
```

Компоненты должны строиться на токенах, извлечённых и переосмысленных из опубликованного сайта. Нельзя использовать старый generated HTML/CSS как permanent architecture.

Astro-компонент должен выражать смысл блока:

```text
RobotHero
RobotPricing
CollectionFAQ
LeadForm
ArticleAside
```

а не быть бессмысленной обёрткой над экспортированными классами.

### 8.7. Astro и медиабиблиотека

Astro потребляет media library и выводит изображения согласно их роли:

| Role | Где используется |
|---|---|
| `hero` | hero карточки/подборки/кейса |
| `card` | каталожная карточка |
| `gallery` | галерея |
| `OG` | Open Graph / Twitter image |
| `icon` | интерфейсные элементы |
| `decorative` | не meaningful image |

Компоненты не должны случайно брать hero-фото как card image, если для карточки есть отдельная square product image.

### 8.8. Astro и формы

Astro отображает UI формы и CTA-контракты, но не должен сам хранить секреты и не обязан быть backend.

Разделение:

```text
Astro
  → form UI
  → поля формы
  → validation hints
  → consent checkbox
  → analytics event contract

Backend/integration layer
  → captcha verification
  → Telegram delivery
  → amoCRM duplicate
  → secret handling
  → error logging
```

До подключения backend/integration layer форма может быть отрисована как disabled/deferred, чтобы не создавать ложное ощущение работающей отправки.

### 8.9. Astro и Кибер Гоша

Astro предоставляет публичный content/RAG surface для Кибер Гоши:

- карточки роботов;
- FAQ;
- статьи;
- подборки;
- новости;
- кейсы;
- structured data;
- CTA context.

Сам RAG-бот — отдельный runtime/integration layer. Astro даёт ему базу знаний и точку встраивания на сайте.

### 8.10. Astro и Гефест

Гефест управляет Astro-проектом через GitHub:

```text
задача / SEO-пакет / правка
→ Гефест меняет data/content/components
→ запускает Astro build
→ запускает validators
→ создаёт commit/push после подтверждения
```

Гефест не заменяет Astro. Он является агентом сопровождения, который работает с Astro-кодом, данными, документами и quality gates.

### 8.11. Astro и production

Production delivery:

```text
npm --prefix app run build
→ app/dist
→ Docker/Nginx
→ Coolify/Traefik
→ kiber-portal.ru
```

Astro не должен напрямую менять DNS, Coolify, analytics IDs, Telegram bot tokens или amoCRM credentials. Эти действия относятся к deployment/integration layer и требуют отдельного approval.

## 14. Forms and lead-flow

### 13.1. Два типа кнопок

На сайте присутствуют два основных CTA-типа:

1. **«Написать нам»**  
   Открывает попап с кнопками Telegram / WhatsApp / Max. Кнопки переводят в соответствующий мессенджер.

2. **«Оставить заявку»**  
   Открывает попап формы.

### 13.2. Lead form

Форма заявки:

- имя — обязательное;
- телефон — обязательное;
- captcha / anti-spam — обязательный слой;
- email можно использовать как необязательное поле, если форма расширяется;
- форма должна уходить в Telegram-чат;
- форма должна дублироваться в amoCRM.

### 13.3. Anti-spam

Требования:

- captcha;
- server-side validation;
- rate limiting;
- honeypot можно добавить как дополнительный слой;
- защита от пустых/массовых отправок;
- логирование ошибок без сохранения секретов.

### 13.4. Telegram / amoCRM delivery

Telegram:

- сообщение в чат/тред менеджеров;
- поля: имя, телефон, страница, robot/context, UTM, время;
- секреты не хранятся в Git.

amoCRM:

- lead duplicate после Telegram;
- pipeline/status/responsible user настраиваются отдельно;
- tokens/webhooks не хранятся в Git.

Публичный Кибер Гоша работает с клиентом.

## 23. Итоговая целевая система

КИБЕР ПОРТАЛ должен стать не просто сайтом-витриной, а структурированной коммерческой платформой:

```text
SEO + каталог аренды + магазин + подборки + статьи + новости + кейсы + медиа + PDF-КП + формы + мессенджеры + чат-бот + агенты + аналитика + GitHub workflow
```

Главная архитектурная идея:

```text
структурированные данные
  -> компоненты Astro
  -> SEO-страницы
  -> CTA/lead-flow
  -> аналитика
```
