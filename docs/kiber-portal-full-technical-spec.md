## 1. Назначение сайта

### 1.1. Главная бизнес-цель

Главная цель сайта — **получать заявки на аренду роботов**.

Сайт должен быть не просто каталогом и не просто блогом, а коммерческой системой, которая:

- объясняет, какие роботы доступны;
- помогает выбрать робота под событие;
- вызывает доверие;
- переводит посетителя в контакт с менеджером;
- поддерживает SEO-трафик по коммерческим и информационным запросам;
- становится базой знаний для публичного чат-бота Кибер Гоши и внутреннего ассистента Гефеста.

### 1.2. Дополнительные цели

Дополнительные цели сайта:

1. **SEO-трафик**  
   Привлекать коммерческий и информационный трафик по запросам аренды/проката роботов, конкретных моделей, сценариев мероприятий и новостей робототехники.

2. **Доверие и портфолио**  
   Показывать реальные роботы, фото, кейсы, юридические данные, понятный процесс аренды, ответы на вопросы и proof-контент.

3. **Каталог как витрина**  
   Давать быстрое представление о роботах, сценариях и возможностях, даже если итоговая цена и подбор уточняются менеджером.

4. **Редакторская и агентская управляемость**  
   Сайт должен быть удобен для обновления через GitHub и ассистента Гефеста после подтверждения изменений.

### 1.3. Conversion actions

Главный conversion action:

```text
Написать нам в мессенджер
```

Дополнительные conversion actions:

- отправить форму заявки;
- позвонить;
- подобрать робота через чат-бота;
- скачать PDF-КП;
- перейти в карточку робота из каталога/подборки/статьи;
- задать вопрос по конкретной странице или роботу.

### 1.4. Основная аудитория

Основная аудитория:

- event-агентства;
- корпоративные клиенты.

Дополнительная аудитория:

- частные мероприятия;
- выставки и форумы;
- рестораны и HoReCa;
- школы и детские события;
- организаторы промо-акций;
- подрядчики и партнёры по мероприятиям.

### 3.2. Обязательный будущий тип страниц: Кейсы

Раздел **Кейсы** является обязательным будущим типом страниц.

Кейс — это страница реального мероприятия или проекта, где фиксируются:

- название события;
- дата/период, если можно публиковать;
- город/площадка, если можно публиковать;
- робот или несколько роботов;
- сценарий использования;
- фотографии/видео;
- результат;
- отзыв или цитата, если есть разрешение;
- ссылки на карточки роботов и релевантные подборки;
- CTA «Повторить похожий сценарий».

Кейсы нужны как proof layer для доверия, SEO и sales enablement.

## 4. SEO-архитектура

### 4.1. Роли разделов в SEO

| Тип страницы | SEO-роль | Search intent |
|---|---|---|
| Главная | ВЧ: аренда/прокат роботов | Commercial / transactional |
| Карточки роботов | НЧ модельные запросы | Transactional / model-specific |
| Подборки | СЧ группы и сценарии | Commercial investigation |
| Блог Кибер Гоши | НЧ сценарные и идейные запросы | Informational + assisted commercial |
| Новости | Инфотрафик и узнаваемость | Informational / freshness |
| Кейсы | Proof + сценарные запросы | Commercial proof / trust |
| Контакты | Брендовые и доверительные запросы | Navigational / trust |

### 4.2. Региональная SEO-структура

Базовые регионы:

- Москва;
- Россия.

Региональная структура не должна плодить пустые doorway-страницы. Страницы формата:

```text
/robot-na-vystavku-v-moskve
/arenda-robota-na-svadbu-v-moskve
```

создаются только если есть:

- подтверждённые реальные запросы пользователей;
- достаточный уникальный контент;
- релевантный робот/сценарий;
- полезная коммерческая ценность;
- отсутствие каннибализации с подборками/статьями.

Такие страницы могут существовать как статьи, подборки или отдельные landing pages — решение зависит от intent.

### 4.3. Schema.org

Обязательные schema types:

- `Organization`;
- `WebSite`;
- `Service` для карточек роботов/услуг;
- `FAQPage` для страниц с FAQ;
- `BreadcrumbList`;
- `CollectionPage` для подборок и индексов;
- `BlogPosting` для статей;
- `ContactPage`;
- `NewsArticle` или `BlogPosting` для новостей — в зависимости от формата;
- `Product` допустим для магазина товаров, но не должен подменять аренду услуг.

### 4.4. Alt и media SEO

Для всех meaningful images нужен truthful alt.

Правила:

- сначала описываем, что реально видно;
- коммерческие ключи добавляем только если они соответствуют изображению и странице;
- не превращаем alt в список ключей;
- не добавляем неподтверждённые города, бренды, площадки, людей, кейсы;
- не пишем цены в alt;
- для каждой страницы/контекста должна быть достаточная коммерческая SEO-alt coverage по meaningful images.

### 4.5. PDF-КП и SEO

Отдельный SEO-слой для PDF-КП не является обязательным.

PDF-КП — это sales/support инструмент, который формируется на основе карточки робота/услуги и может включать:

- название робота/услуги;
- сценарии применения;
- что входит в аренду;
- требования к площадке;
- фото;
- ориентировочную цену или `цена по запросу`;
- контакты;
- юридическую пометку, если цена не является офертой.

PDF может быть закрыт от индексации или генерироваться по запросу, чтобы не плодить дубли SEO-страниц.

## 5. Page types

### 5.1. Home page

Задача главной:

- быстро объяснить, что КИБЕР ПОРТАЛ сдаёт роботов в аренду для мероприятий;
- показать каталог;
- дать быстрый CTA в мессенджер;
- направить в подборки;
- показать Кибер Гошу как голос бренда;
- дать вход в статьи/новости;
- создать доверие.

Обязательные блоки:

1. Header.
2. Hero с ВЧ positioning.
3. Каталог аренды роботов.
4. Блок Кибер Гоши.
5. Подборки.
6. Статьи/Блог Кибер Гоши.
7. CTA/lead-flow.
8. Footer.

### 5.2. Robot rental card

Карточка робота — главная коммерческая endpoint-страница под модельный НЧ запрос.

Обязательные блоки:

1. Hero.
2. Короткий вводный текст с самой важной информацией.
3. Факты.
4. Сценарии применения.
5. Галерея.
6. Видео, если есть.
7. Тарифы/цена.
8. FAQ.
9. Похожие роботы.
10. Статьи про робота.
11. PDF-КП.
12. CTA.
13. Требования к площадке.
14. Что входит в аренду.
15. Доставка/оператор.
16. Юридическая пометка рядом с ценами.

Цены:

- основной вариант — цены могут быть скрыты, сайт ведёт в заявку;
- если цена показывается, используется формат `от X ₽ / час`;
- пакеты 1/4/8 часов показываются при необходимости;
- если цена неизвестна или зависит от условий, блок цены заменяется на `цена по запросу`;
- запрет на показ цены в ТЗ не нужен, нужна поддержка состояния `цена по запросу`.

### 5.3. Shop product card

Отдельно от аренды должен быть предусмотрен будущий каталог-магазин:

- продажа роботов;
- запасные части;
- АКБ;
- аксессуары;
- расходники;
- другие товары.

Карточка товара магазина не должна смешиваться с карточкой аренды.

Обязательные поля товара:

- title;
- slug;
- category;
- brand/model;
- availability status;
- price или request price;
- images;
- specs;
- compatibility;
- warranty/terms;
- CTA: купить/запросить наличие/получить консультацию.

Подборки — landing pages под заявки, но обязательно SEO-оптимизированные.

Архитектура должна позволять создавать любые тематические подборки в любое время.

Стартовые подборки:

- роботы-гуманоиды;
- роботы-собаки;
- роботы для свадьбы;
- роботы для выставки;
- роботы для корпоратива;
- роботы для промо;
- роботы-официанты;
- роботы-художники;
- роботы для детей;
- роботы для welcome-зоны;
- интерактивные роботы;
- роботы для ресторанов/HoReCa.

Обязательные блоки подборки:

1. Hero.
2. Короткое объяснение сценария.
3. Список подходящих роботов.
4. Рекомендации выбора.

8. Ссылки на статьи и кейсы.
9. CTA «Написать нам» / «Оставить заявку».

### 5.5. Blog article

Раздел называется **Блог Кибер Гоши**.

Статьи решают задачи:

- scenario long-tail SEO;
- объяснить выбор робота;

## 7. Design system

### 7.1. Источник визуального направления

Визуальный слой должен быть разработан с нуля, но основываться на существующем опубликованном сайте.

Требования:

- не копировать blindly generated HTML/CSS;
- извлекать реальные визуальные паттерны из опубликованного сайта;
- строить собственную design system на токенах и компонентах;
- сохранить узнаваемость КИБЕР ПОРТАЛА;
- улучшить структурность, mobile и SEO.

### 7.2. Базовые визуальные принципы

Зафиксированные ориентиры:

- CTA resting color: `#0088FF`;
- deep/hover/gradient: `#005EFF`;
- основной canvas: `#F4F8FF`;
- hero: фото + graphite scrim, не generic SaaS gradient;
- live font direction: Gillroy/Arial sans-serif;
- secondary font: Montserrat для meta/footer/prices;
- base radius карточек/медиа: 18px;
- product panels могут иметь больший radius;
- не использовать тяжёлые generic shadows;
- catalog robot tiles — отдельные square product images, не hero/gallery photos по умолчанию.

### 7.3. Responsive

Сайт должен проектироваться desktop/mobile одновременно.

Для каждого компонента должны быть определены:

- desktop layout;
- tablet behavior;
- mobile stacking;
- media crop rules;
- CTA placement;
- modal behavior;
- accessibility behavior.

## 8. Content/data model

### 8.1. Общий принцип

Сайт должен быть source-of-truth driven.

Компоненты не должны содержать бизнес-факты напрямую, если эти факты относятся к роботам, тарифам, медиа, SEO, кейсам, статьям или контактам.

### 8.2. Основные datasets / collections

| Entity | Назначение |
|---|---|
| `robots` | аренда роботов |
| `shopProducts` | продажа роботов/запчастей/АКБ/аксессуаров |
| `collections` | подборки |
| `articles` | Блог Кибер Гоши |
| `news` | новости |
| `cases` | кейсы |
| `mediaLibrary` | изображения/видео/alt/caption/roles |
| `tariffs` | тарифы и price status |
| `faq` | FAQ по роботам/страницам |
| `legalPages` | юридические документы |
| `analyticsEvents` | карта событий |
| `integrations` | Telegram/amoCRM/Yandex config contracts |
| `redirects` | old URL -> new URL |

### 8.3. Status semantics

Для спорных данных нельзя использовать пустые строки или `0` как смысл.

Рекомендуемые статусы:

```text
approved
needs_review
generated_needs_review
request
not_applicable
missing
deferred
rejected
```

Для цен:

- `active` — цена есть и может показываться;
- `request` — `цена по запросу`;
- `not_applicable` — тариф не применяется;
- `needs_review` — нужно подтверждение.

## 13. Forms and lead-flow

### 13.1. Два типа кнопок

На сайте присутствуют два основных CTA-типа:

1. **«Написать нам»**  
   Открывает попап с кнопками Telegram / WhatsApp / Max. Кнопки переводят в соответствующий мессенджер.

2. **«Оставить заявку»**  
   Открывает попап формы.

### 13.2. Lead form

Форма заявки:

- имя — обязательное;
- телефон — обязательное;
- captcha / anti-spam — обязательный слой;
- email можно использовать как необязательное поле, если форма расширяется;
- форма должна уходить в Telegram-чат;
- форма должна дублироваться в amoCRM.

### 13.3. Anti-spam

Требования:

- captcha;
- server-side validation;
- rate limiting;
- honeypot можно добавить как дополнительный слой;
- защита от пустых/массовых отправок;
- логирование ошибок без сохранения секретов.

### 13.4. Telegram / amoCRM delivery

Telegram:

- сообщение в чат/тред менеджеров;
- поля: имя, телефон, страница, robot/context, UTM, время;
- секреты не хранятся в Git.

amoCRM:

- lead duplicate после Telegram;
- pipeline/status/responsible user настраиваются отдельно;
- tokens/webhooks не хранятся в Git.

## 14. Bots / agents

### 14.1. Кибер Гоша публичный

Кибер Гоша на сайте — это несколько ролей:

- персонаж/голос бренда;
- чат-бот консультант;
- RAG-агент по каталогу;
- агент подбора робота;
- агент для SEO/news.

Публичный бот должен:

- подобрать робота по мероприятию;
- ответить по ценам, если информация есть в базе;
- собрать заявку;
- передать заявку в Telegram/amoCRM;
- предложить PDF-КП;
- объяснить отличия роботов;
- отвечать только по базе сайта;
- не выдумывать цены, наличие, кейсы, площадки, юридические факты.

### 14.2. Гефест внутренний

Гефест — внутренний ассистент сайта/аналитики/интеграций.

Функции:

- обновляет GitHub после подтверждения;
- ведёт структуру сайта;
- помогает с SEO;
- анализирует QA gates;
- готовит новости/статьи/подборки;
- не ведёт клиентские коммуникации;
- не выступает бизнес-директором;
- не подключает production-инфраструктуру без approval.

### 14.3. Агентская граница

Публичный Кибер Гоша работает с клиентом.  
Внутренний Гефест работает с сайтом, данными, GitHub, аналитикой и интеграциями.

## 15. Analytics/events

### 15.1. Аналитический стек

В ТЗ закладывается только Яндекс-стек:

- Яндекс.Метрика;
- Яндекс.Вебмастер;
- другая аналитика Яндекса при необходимости.

GA4, VK pixel, Umami, Calltouch и другие системы не являются базовым требованием.

### 15.2. Обязательные события

Обязательные события:

- клик по телефону;
- переход в Telegram;
- переход в WhatsApp;
- переход в Max;
- отправка формы;
- скачать PDF-КП;
- scroll depth.

Рекомендуемые дополнительные события:

- открыть попап;
- закрыть попап;
- клик по robot card;
- клик по подборке;
- клик по related article;
- просмотр gallery/video;
- chatbot start;
- chatbot lead created.

### 15.3. Event contract

Каждый CTA должен иметь provider-neutral event contract:

```text
data-analytics-event
data-analytics-source
data-page-type
data-placement
data-robot-slug, если применимо
```

Провайдер Яндекс подключается поверх этого контракта, а не вшивается хаотично в компоненты.

## 17. Legal/compliance

Обязательные юридические страницы:

- политика обработки персональных данных;
- согласие на обработку персональных данных;
- cookie policy;
- пользовательское соглашение.

Обязательные элементы:

- чекбокс согласия у формы;
- ссылка на политику обработки персональных данных;
- текст “не является публичной офертой” рядом с ценами;
- cookie banner для Яндекс.Метрики;
- возможность отключить/не загружать аналитику до согласия, если это требуется выбранной политикой cookie.

Юридические факты должны извлекаться из юридических документов, а не вводиться вручную без источника.

## 18. Validation / quality gates

Сайт должен иметь rendered-output validation, а не только проверку исходных данных.

Обязательные gates:

- build success;
- public pages SEO validation;
- whole-site static validation;
- rendered image alt audit;
- rendered heading audit;
- rendered schema audit;
- rendered social metadata audit;
- rendered CTA/lead-flow audit;
- route inventory;
- robot SEO/internal linking validation;
- collection validation;
- content index/detail validation;
- production readiness matrix.

Публичные страницы должны проверяться отдельно от preview/noindex routes.

Preview/parity/system routes:

- не должны блокировать public SEO gates;
- должны быть `noindex,nofollow`;
- не должны попадать в sitemap как конкуренты финальных страниц.

## 19. Production/deployment boundaries

Production actions запрещены без явного approval.

Нельзя без подтверждения:

- менять DNS;
- деплоить в Coolify production;
- активировать редиректы;
- подключать аналитику;
- подключать реальные lead destinations;
- трогать чужие контейнеры/секреты/аналитику/DNS;
- хранить секреты в Git.

Для AI Class/Coolify:

- использовать только Alex-owned зоны;
- имена контейнеров/app folders с префиксом `alex-*`;
- не устанавливать второй Coolify;
- не трогать shared Coolify/Traefik/Hermes/AI Class services.

## 20. Content management

Сайт должен обновляться через ассистента/Гефеста, который меняет GitHub после подтверждения.

Целевая модель:

```text
пользователь / редактор / SEO-пакет
  -> Гефест анализирует
  -> предлагает изменения
  -> после подтверждения меняет GitHub
  -> запускает QA gates
  -> создаёт commit/push
```

Контентные изменения должны оставлять trace:

- что изменилось;
- источник;
- какие страницы затронуты;
- какие validators прошли;
- что осталось `needs_review`.

## 22. Итоговая целевая система

КИБЕР ПОРТАЛ должен стать не просто сайтом-витриной, а структурированной коммерческой платформой:

```text
SEO + каталог аренды + магазин + подборки + статьи + новости + кейсы + медиа + PDF-КП + формы + мессенджеры + чат-бот + агенты + аналитика + GitHub workflow
```

Главная архитектурная идея:

```text
структурированные данные
  -> компоненты Astro
  -> SEO-страницы
  -> CTA/lead-flow
  -> аналитика
  -> агенты Кибер Гоша / Гефест
```

Каждая страница и каждый компонент должны иметь понятную роль: привлечь, объяснить, доказать, подобрать, конвертировать или поддержать SEO/бота.
